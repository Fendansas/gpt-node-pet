### Что я ответил (своими словами)

1. **Слои:** репозиторий умеет общаться с базой (Mongoose) и только обращается к ней. Сервис отвечает за логику и не обязан знать, как работать с БД, — ему лишь нужны данные. Если поменяем БД — добавим новый репозиторий.
2. **Ошибки:** ошибка ловится и передаётся в центральный обработчик, который отдаёт статус и сообщение об ошибке.
3. **JWT login:** POST на логин → рейт-лимит → валидация полей → контроллер → сервис находит юзера → проверяет пароль → генерит токен → отправляет клиенту. `tokenVersion` нужна, чтобы можно было отменить работающий токен (logout-all, деактивация юзера).
4. **Валидация:** в `req.body` попадут только ожидаемые данные; если проверка не прошла — ошибка. Перезаписываем, чтобы дальше были только нужные данные.
5. **Цепочка:** сначала определяем юзера и может ли он смотреть задачи, потом проверяем page/limit; всё проверенное через один `req` попадает в контроллер в безопасном виде.
6. **Асинхронность:** Node однопоточная, но работа с файлами обрабатывается отдельно; event loop раскидывает всё по очередям, пока промисы выполняются — отдаёт данные клиенту; сервер может зависнуть на гигантском переборе массива.
7. **Rate limiter:** при перезагрузке лимиты обнуляются; «Map очищается сам» (оказалось неверно).
8. **404:** на несуществующий роут вернётся 404.
9. **PORT/.env:** хостинги назначают порт сами → пишем в env. `.env` нельзя класть в репозиторий, только пример-шаблон.
10. **Пароль:** `select:false` — пароль не возвращается при обычном селекте; `.select('+password')` — явно хотим его получить (для логина); `userResponse` — отдаём только то, что нужно фронту.
11. **Статусы:** переход `draft→review` → `ForbiddenError('Invalid status transition')`. Таблица переходов нужна, чтобы задача не стала готовой сразу. По `req.user` всегда знаем роль и кто шлёт запрос — проверяем права.
12. **Гонки:** третий аргумент — защита от перезаписи: проверяем, что статус в БД такой же, как в начале запроса. Второму запросу — `ConflictError('Task was modified by another request')`. БД гарантирует атомарность, а эта проверка — дополнительный уровень контроля.
13. **Блокировка на лету:** деактивированный юзер блокируется сразу, потому что `authMiddleware` каждый раз проверяет `isActive` (`if (user.isActive === false) return next(new ForbiddenError('Forbidden'))`).
14. **11000:** в `createUser` (и `updateUser`) ловим дубликат почты → `ConflictError('Email already exists')`; другие коды пробрасываем `throw error`.
15. **Пагинация:** 12 задач при limit 5 → 3 страницы (5/5/2), `totalPages = Math.ceil(12/5) = 3`. Отдаём `total` и `totalPages`, чтобы фронт строил кнопки пагинации.

### Что поправил / дополнил учитель

1. **404 vs 401 (утечка):** в `user.service.js` нет почты → 404, неверный пароль → 401. Атакующий может понять, зарегистрирована ли почта. Правильно — **401 в обоих случаях** с одинаковым сообщением `'Invalid credentials'`.
2. **asyncHandler точнее:** `handler(req,res,next).catch(next)` — `next(err)` говорит Express «это ошибка», цепочка пропускается, ошибка уходит сразу в центральный обработчик (`app.js:13-50`), который читает `err.statusCode`.
3. **tokenVersion технически:** версия вшита в JWT при логине (`user.service.js:55-62`), auth-мидлварь сравнивает с версией юзера в БД (`auth.middleware.js:40-42`). Поставил новую цифру в БД — все старые токены умерли.
4. **Zod strip:** `safeParse` по умолчанию вырезает все лишние поля (`hacked`, `__proto__`) — защита от prototype pollution. Дальше в слои попадают только ожидаемые данные.
5. **req — общая «корзина»:** в Express это один и тот же объект на всю цепочку; каждый middleware мутирует его (auth → `req.user`, validateQuery → `req.validatedQuery`). authMiddleware проверяет **личность**, а права на таски — уже в сервисе.
6. **Event loop уточнение:** сеть/БД — асинхронные системные операции (ядро ОС уведомляет); файлы (`fs`) — пул потоков libuv (≈4). Продолжение `await` после резолва промиса — микрозадача.
7. **Rate limiter — НЕ чистится:** в коде нет `delete`/TTL, каждая новая IP добавляется в `Map`, память растёт безгранично. 2 инстанса = 2 независимых `Map` → защита деградирует (5 попыток на инстанс). Нужен общий стор (Redis) или лимитер на балансировщике.
8. **404:** кастомный обработчик ошибок НЕ вызывается (срабатывает только на `next(err)`). На несуществующий роут отвечает встроенный finalhandler Express текстом `Cannot GET ...` — формат выбивается из API. Решение: явный catch-all `app.use((req,res)=>res.status(404).json({...}))` перед обработчиком ошибок.
9. **PORT:** стандарт — `process.env.PORT || 3333`. Секреты — в `.env.example` (пустые заглушки), на проде — через секрет-менеджер хостинга.
10. **Defense in depth:** `select:false` + `userResponse()` — даже если забудут про select, наружу уйдёт только белый список. Мелочь: `getUsersAssignable` (`user.repository.js:77-79`) отдаёт сырые документы — нарушение правила.
11. **canChangeStatus:** комбинации вне мапы `taskStatusPermissions` → `return false` (`taskStatusPermissions.js:16`) → ForbiddenError.
12. **Optimistic lock:** валидация прошла до гонки, но `findOneAndUpdate` со `status: oldStatus` обновит только первого; второй получит `null` → `ConflictError`. БД — атомарность, проверка в сервисе — контроль бизнес-уровня.
13. **Stateless vs живой юзер:** `jwt.verify` проверяет только подпись и срок — он не знает про деактивацию. Поэтому `authMiddleware` на каждый запрос делает `getUserById` (`auth.middleware.js:33`) и сверяет: юзер существует (37), `tokenVersion` совпал (40), `isActive` (44). Цена — запрос в БД на каждый запрос; выгода — мгновенная блокировка и отзыв токенов.
14. **Перевод ошибок 11000:** уникальный индекс по `email` → драйвер кидает `MongoServerError` c `code === 11000` (`user.repository.js:18-20`). Перевод в `ConflictError('Email already exists')` не даёт утечь внутренностям БД и даёт клиенту читаемое сообщение + 409. `throw error` (строка 21) — предохранитель: неизвестный код нельзя «переводить» или глотать, иначе незнакомая ошибка молча развалит ответ.
15. **Пагинация:** `page=999` → `skip(4990).limit(5)` → пустой `tasks: []`, но валидный 200; фронт по `totalPages: 3` понимает, что страницы за пределами, и не рисует пустоту.

### Мои слабые места (что повторить)

- Статусы ошибок у логина: 404 не путать с 401.
- Rate limiter: не заметил, что `Map` никогда не чистится.
- Не был уверен про несколько инстансов (общая память vs раздельные `Map`).
- Не знал про catch-all 404 и что Express сам отвечает за несуществующие роуты.
- Пагинация: не назвал формулы `skip`/`totalPages` сам (потребовалась подсказка на `totalPages`).

### Что я ответил (своими словами)

1. **Коды успеха:** 200 — всё хорошо, 201 — что-то создано; при успешном POST на задачу ответ должен быть 201; 404 значит что-то не найдено (например, юзер на которого осайняют задачу).
2. **Файлы:** первый middleware проверяет размер/тип и загружает файл; второй — есть ли файл вообще, иначе `BadRequestError('Bad request')`; третий проверяет формат содержимого. Проверки mimetype мало — его можно подделать, нужно убедиться, что формат верный по содержимому. Если неверный — удаляем файл, чтобы не хранить мусор.
3. **history:** увидел, что функционала нет — только поле в модели.
4. **validateObjectId:** mongoose проверяет, валидный ли id; если нет — `ValidationError('Invalid task id')`. Без middleware уйдёт `NotFoundError` (оказалось неверно — будет CastError). Бонус-инсайт: не делаем лишний запрос в БД. Заметил, что в `task.routes.js` у `validateObjectId` нет второго аргумента — надо починить.
5. **Индексы:** `createdBy: 1` — по возрастанию, `status: 1` — тоже, `createdAt: -1` — по убыванию. Монго строит дерево, упорядоченное по createdBy → status → createdAt (как имя → фамилия → дата). На вопрос про запрос админа по одному status: «индексы не сработают, потому что они работают в связке» (оказалось верно). Сказал, что тема сложная, нужно разбирать подробнее.
6. **logout / мягкое удаление:** logout работает, потому что клиент сам удаляет токен у себя; 204 без тела — стандарт для logout. logout-all меняет tokenVersion → не смогут зайти все устройства, даже если токен украден. logout выходит только с одного устройства, украденный токен живёт до истечения времени. Юзер не удаляется, потому что такая задумка: прячем его, но данные остаются, чтобы можно было быстро вернуть; при полном удалении пришлось бы заново заполнять данные.

### Что поправил / дополнил учитель

1. **204 = «успех без тела».** Успешные коды — это контракт для фронта: `deleteTask` c 200+body — семантическая ложь, `createTask` c 200 сломает клиент, который ветвится по 201.
2. **Точный порядок файлов:** мультер (`dest: 'uploads/'`) пишет файл на диск ещё до `requireFile`. `requireFile` только проверяет, что `req.file` появился. `file.mimetype` формирует клиент (подделывается), `fileTypeFromFile` читает магические байты — их почти не подделать. Очистка мусора сделана дважды: в `validateFileContent` и в контроллере при падении сервиса (`task.controller.js:59-67`).
3. **Схема ≠ реализация:** поле в модели без кода в сервисе — мёртвый груз «под будущее»; в `task.service.js` нет ни одного упоминания `history`.
4. **400 vs 404 для id:** мальформный id (`abc`) → Mongoose бросает **CastError** (fail-fast до запроса), центральный обработчик отдаёт 400 с сырым сообщением (утечка). Валидный по формату, но отсутствующий id → **NotFoundError → 404**. `ObjectId.isValid` проверяет только формат, не существование.
5. **Индексы:** leftmost prefix — Mongo идёт по индексу слева направо, в середину «прыгнуть» не может; запрос по одному `status` без createdBy/assignedTo индекс не использует — коллекция сканируется.
6. **logout vs logout-all:** `logout` ничего сервер не инвалидирует (клиент сам стирает токен; украденный живёт до часа); `logout-all` бампает tokenVersion в БД — умирают все токены сразу. Мягкое удаление сохраняет связи (createdBy/assignedTo остаются валидными), но не исполняет «право быть забытым» (GDPR).

### Мои слабые места (что повторить)

- Индексы: понял идею упорядочивания, но нужен углублённый разбор (.explain()).

1. **Логин — 401, а не 404:** утечка не в тексте сообщения, а в **разном статусе**: почты нет → 404, пароль неверный → 401, деактивация → 403. Атакующий отличает причину. Правильно — 401 `Invalid credentials` во всех неуспешных случаях. (Слабое место Дня 1 всплыло снова.)

7. **buildTaskChanges — точная причина:** ObjectId — **объект**, `!==` сравнивает по ссылке, поэтому даже при равных значениях дал бы «изменено». Сравнение через `String(...)` сравнивает значения.
8. **$push — атомарность, а не «проще»:** один `findOneAndUpdate` = атомарная операция на уровне документа (либо всё, либо ничего). Это **быстрее** (один round-trip), а не медленнее. Два запроса → частичный сбой → нужен откат/компенсация или транзакция.
9. **Схема history:** верно. Неизвестное поле вырезается (`strict: true`), whitelist + валидация.
10. **runValidators:** верно. При `findOneAndUpdate` валидаторы по умолчанию **не** запускаются — особенность Mongoose.
11. **Индексы — поправка:** у **админа** фильтр пустой → **ни один индекс** не сработает (COLLSCAN). У **юзера** фильтр `$or: [{createdBy}, {assignedTo}]` → используются **оба** индекса (по одному на ветку). Leftmost prefix: индекс `{a,b,c}` обслуживает запросы по `a`, `a+b`, `a+b+c`, но не по одному `b`/`c`.
12. **explain:** `createdAt: -1` в индексе позволяет пройти по индексу в порядке «новые сверху» **без отдельной сортировки в памяти**. `.explain()`: `stage` = COLLSCAN/IXSCAN; `nReturned` — сколько вернули; `totalDocsExamined` — сколько документов перебрали; `totalKeysExamined` — сколько записей индекса. Признак плохого запроса: `totalDocsExamined` огромен, а `nReturned` мало.
13. **DELETE /users/me — варианты точнее:** каскадное удаление, **аннимизация** (заменить PII, оставить документ — GDPR), обнуление ссылок, архив. «Право на забвение» стирает персональные данные, но бизнес-данные (задачи) часто хранят.
14. **Код-ревью:** новое поле сначала вырезает Zod (`safeParse` strip), потом проверка в `buildTaskChanges` — двойная защита. В `cancelTask` бага нет: гард `status === 'cancelled'` гарантирует непустой `changes`. Но проверки `Object.keys(changes).length > 0` нет — несимметричность с `updateTask`.

## День 5 — 2026-10-21

### Темы дня

1. Optimistic lock: почему для админа не передаётся `expectedStatus` (`task.service.js:185-196`).
2. Составные индексы + `.explain()`: `$or` и два индекса, сортировка vs середина ключа, COLLSCAN.
3. AsyncHandler в Express 5: нужен ли, синхронный `throw` vs async rejection.
4. Event loop: синхронный `while` на 3 секунды, `fs.readFile` и пул потоков, `bcrypt` и блокировка.
5. `JWT_SECRET === undefined`: поведение `jwt.sign`/`jwt.verify`, fail-fast проверка при старте.

### Что я ответил (своими словами)

1. **Optimistic lock:** «потому что админ может делать всё; получит второй, кто нажал обновить; у нас помимо этой защиты есть ещё защита в базе данных».
2. **Индексы:** индекс не сработает, потому что «сортируем только по статусу, а нужно по всем параметрам; сортировка должна идти слева направо, а не с середины». Плохой запрос — «если выбирать не с первого, то есть не слева направо».
3. **AsyncHandler:** правило устоявшегося стиля; приложение теоретически может работать на Express 4, там он используется в полной мере. Синхронный `throw`: «думаю, попадёт в обработчик ошибок и будет словлен».
4. **Event loop:** сервер подвиснет на 3 секунды, ничего больше обрабатываться не будет. `fs.readFile` не блокирует — «Нода передаёт задачу в пул потоков и сразу освобождает основной поток, когда прочитано — возвращается в виде колбэка». `bcrypt.hash`: «да, блокирует, и это определённая защита от взлома — серверу нужно время на выполнение этого действия».
5. **JWT_SECRET:** сервер упадёт с 500 («ошибка, что секрет должен иметь значение»), зайти не сможет, придётся заново логиниться. «В идеале сервер сразу должен выкинуть ошибку — можно сделать проверку на наличие этих переменных».

### Что поправил / дополнил учитель

1. **Optimistic lock — механика гонок:** для двух не-админов второй получает `ConflictError` (фильтр `{_id, status: old}` не совпал). Для двух админов `expectedStatus` не передаётся → фильтр только `{_id}` → **оба succeed, last write wins**, ConflictError нет. Админ+не-админ: если админ записал первым — не-админ получит ConflictError; если не-админ первым — админ спокойно перетирает. «Защита в БД» — только атомарность `findOneAndUpdate` (один документ), но БД **не знает про статус-машину**: без `status` в фильтре она перезапишет. Осознанный компромисс: админу нужно финальное состояние в любом случае. Тонкость: `buildTaskChanges` сравнивает с прочитанным до гонки `task` → в `history` может записаться устаревший `from` (аудит врёт при гонке).
2. **Индексы — что ученик не ответил:** фильтр `{status:'done', $or:[{createdBy},{assignedTo}]}` → ветка `createdBy` идёт по `{createdBy, status, createdAt}`, ветка `assignedTo` — по `{assignedTo, status, createdAt}`; каждая ветка свой IXSCAN, потом слияние. Сортировка по `createdAt` читается из индекса **только если все поля слева закреплены equality**: с `?status=done` — equality и по createdBy, и по status → in-memory SORT нет ✅; без статуса (`GET /tasks?sort=-createdAt`) — status между ними плавает → порядок createdAt сломан → блокирующая сортировка / COLLSCAN+SORT ⚠️. Админ `{status:'done'}` → оба индекса начинаются с createdBy/assignedTo, status — второе поле, прыгнуть в середину нельзя (leftmost prefix) → **COLLSCAN**. Пара метрик плохого запроса: **`totalDocsExamined` ≫ `nReturned`** (+ `stage: COLLSCAN`).
3. **AsyncHandler:** в Express 5 промис-отказ **встроенно** уходит в `next(err)` — asyncHandler избыточен (защита внахлёст), нужен для портируемости на Express 4 и единообразия. Синхронный `throw`: исход верный (попадёт в обработчик), но механизм — не `.catch(next)`: `handler()` бросает **до** навешивания `.catch`, ошибка промаскивает мимо промиса и ловится **try/catch внутри роутера Express** → `next(err)`. Два мира: sync throw → try/catch роутера; async rejection → `.catch(next)` (или встроенный промис-хендлер Express 5).
4. **Event loop:** 1 верно ✅ (подвисает весь сервер на 3 сек, main thread). 2 mostly верно: пул потоков libuv (≈4) — для **файлов**; уточнение: продолжение после резолва — микрозадача, а **сеть/БД** — не пул потоков, а асинхронные системные вызовы (ядро ОС уведомляет). 3 **неверно:** `bcrypt` тоже кидает расчёт в пул потоков libuv → `await bcrypt.hash(...)` event loop **не блокирует** (иначе параллельные логины морозили бы сервер). «Медленность = защита» — про другое: cost factor 10 делает **перебор паролей** дорогим для атакующего — это защита данных, не availability. Блокируют event loop **синхронный JS** (`while`, большие JSON.parse).
5. **JWT_SECRET:** `jwt.sign(payload, undefined)` бросает `secretOrPrivateKey must have a value` → внутри async-сервиса → rejected promise → 500 **только на `/login`**, сервер жив. Про verify: `jwt.verify(token, undefined)` бросает, но в `auth.middleware.js:27-31` это в `try/catch` → **401 по всему защищённому API** (не 500, не падение процесса — сплошной 401). Fail-fast — падаем до `app.listen`:
   ```js
   if (!process.env.JWT_SECRET) { console.error('FATAL: JWT_SECRET is not set'); process.exit(1); }
   ```
   `process.exit(1)` — ненулевой код для хостинга/докера. Принцип: **конфиг проверяется один раз на старте, а не в рантайме**. Аналогично — `MONGODB_URI`.
